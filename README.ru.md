# tokcount

[English version](README.md)

Подсчёт токенов для LLM-токенизаторов на чистом Go: без cgo, без Rust, без WASM.
Единственная зависимость — `golang.org/x/text` (NFC для Qwen).

Пакет не строит сами токены, только считает их. Результат совпадает с эталонными
реализациями: HF `tokenizers` для `tokenizer.json` и `tokenization_kimi.py`
(tiktoken) самой модели для Kimi.

Подсчёт не выходит за пределы Go, по ходу проверяет контекст и может
остановиться, как только превышен лимит, поэтому огромный вход всегда можно
бросить.

```bash
go get github.com/sokolovb/tokcount
```

До v1 API может меняться.

## Поддерживаемые модели

| Семейство | Файлы | Загрузка | Проверено на |
|---|---|---|---|
| Kimi | `tiktoken.model`, `tokenizer_config.json` | `LoadKimi(dir, opts)` | K3, Kimi Linear (K2, K2.5, K2.6 используют те же файлы и регулярку) |
| DeepSeek | `tokenizer.json` | `LoadHF(path, opts)` | V4.1-Flash, V3.2-Exp (V4-Pro, R1 — та же конфигурация) |
| GLM | `tokenizer.json` | `LoadHF` | GLM-5.3 (GLM-5 = GLM-5.3) |
| Qwen | `tokenizer.json` | `LoadHF` | Qwen3.8, Qwen3 (Qwen3.5 = Qwen3.8) |
| GPT-OSS | `tokenizer.json` | `LoadHF` | gpt-oss-120b |
| Gemma | `tokenizer.json` | `LoadHF` | Gemma 4 |

Другие `tokenizer.json` тоже загрузятся, если используют только поддерживаемые
компоненты. Если в файле встречается неизвестный нормализатор, пре-токенизатор
или конструкция регулярки, `LoadHF` возвращает ошибку, а не считает молча
неправильно. Другие tiktoken-модели загружаются через
`LoadTiktoken(path, TiktokenConfig{Pattern, Specials}, opts)`.

## API

```go
c, err := tokcount.LoadHF("tokenizer.json", nil)

n, err := c.Count(ctx, text)                      // точное число; ctx.Err() при отмене
n, exceeded, err := c.CountUpTo(ctx, text, limit) // остановится, как только n > limit
ok, err := c.Fits(ctx, text, limit)               // когда может, отвечает по одной длине текста
```

- Считается только содержимое, как `encode(text, add_special_tokens=False)`.
  BOS и шаблон чата не добавляются.
- Спецтокены, встретившиеся в тексте (`<|im_end|>` и т.п.), по умолчанию
  считаются как 1 токен, как в эталоне. `Options{SpecialTokensAsText: true}`
  считает их обычным текстом: это `split_special_tokens=True` в HF и
  `allow_special_tokens=False` в Kimi.
- `Counter` безопасен для конкурентного использования. Таблицы неизменяемы,
  кэш подсчётов по словам шардирован и ограничен (`Options.CacheSize`).

## Контроль над выполнением

- Контекст проверяется по ходу работы: в сканировании регулярок, при
  нормализации (кусками по 32 КБ на границах NFC), в построении и слиянии
  символов BPE. При отмене `Count` возвращает `ctx.Err()`. На M4 Pro после
  дедлайна вызов возвращается не позже чем через ~6 мс, в том числе на 10 МБ
  враждебного ввода (пробелы, цифры, одна буква, иероглифы), и эта задержка от
  размера входа не зависит.
- BPE работает через кучу за O(n log n), поэтому даже многомегабайтное «слово»
  без пробелов не уходит в квадратичное время. Худший случай из проверенных —
  около 300 мс на 1 МБ на одном ядре.
- Gemma отдаёт весь текст в BPE одним куском. Пакет режет его в местах, через
  которые не может пройти ни одно слияние: перед `▁` и `\n`, если пары символов
  на границе нет ни в одном токене словаря. Результат тот же, а куски
  становятся словами, которые кэшируются.
- Буферы, раздутые гигантским входом, в пул не возвращаются: разовая
  мегабайтная строка не держит память после вызова.

## Производительность

Текст 1,2 МБ (код, документация, многоязычная проза), одно ядро Apple M4 Pro:

| Модель | tokcount, без кэша | tokcount, с кэшем | эталон (Rust через Python) |
|---|---|---|---|
| DeepSeek V4.1 | 21 МБ/с | 37 МБ/с | 2,9 МБ/с |
| Gemma 4 | 34 МБ/с | 98 МБ/с | 5,1 МБ/с |
| GLM-5.3 | 28 МБ/с | 55 МБ/с | 3,4 МБ/с |
| GPT-OSS | 28 МБ/с | 55 МБ/с | 3,8 МБ/с |
| Qwen3.8 | 22 МБ/с | 44 МБ/с | 3,3 МБ/с |
| Kimi K3 | 24 МБ/с | 44 МБ/с | 13,9 МБ/с (tiktoken) |

Эталон при этом строит сами токены и смещения, так что сравнение не
один-к-одному. Загрузка токенизатора занимает 40–400 мс.

## Тесты

```bash
tools/fetch_models.sh   # файлы токенизаторов в testdata/models, ~170 МБ
go test ./...
go test -race ./...
```

Юнит-тестам больше ничего не нужно. Сверке с эталоном нужны файлы
токенизаторов, которых нет в репозитории: `tools/fetch_models.sh` скачивает их
с Hugging Face Hub ровно тех ревизий, на которых посчитан эталон. Без них
сверка пропускается. `TOKCOUNT_MODELS` задаёт другой каталог.

`TestParity` сверяет 12 конфигураций на 3572 текстах (2,2 млн символов). В корпусе:
сокращения в верхнем регистре, `ſ`, комбинирующие знаки (включая zalgo
длиннее 30 знаков), CJK, эмодзи с ZWJ, NBSP и другие Unicode-пробелы,
управляющие символы, спецтокены внутри текста, длинные серии пробелов,
тексты больше 400k символов (порог нарезки Kimi). Подсчёт идёт параллельно на
одном `Counter`, тесты проходят и под `-race`.

Эталон в `testdata/` пересобирается так:

```bash
python3 -m venv .venv && .venv/bin/pip install -r tools/requirements.txt
.venv/bin/python tools/gen_reference.py
```

Чтобы добавить модель, допишите её в `tools/fetch_models.sh` и в `MODELS` в
`tools/gen_reference.py`.

## Известные ограничения

- **Версия Unicode.** Классы `\p{L}`, `\p{N}` и т.д. берутся из таблиц Go
  (Unicode 15.0). Символы, добавленные в Unicode 15.1/16, могут
  классифицироваться не так, как в эталонных движках.
- **Невалидный UTF-8.** У эталона такого входа не бывает (строки Python всегда
  валидны). Здесь невалидные байты классифицируются как U+FFFD, а BPE работает
  по сырым байтам.
- **Kimi Linear** резервирует 258 спецтокенов вместо 256. `LoadKimi` знает
  о 256, так что текст, содержащий буквально `<|reserved_token_163840|>` или
  `<|reserved_token_163841|>`, посчитается иначе.
- **HF `tokenizer.json`:** не поддерживаются WordPiece, Unigram, ByteLevel со
  встроенной регуляркой GPT-2 и `add_prefix_space`, добавленные токены с
  `single_word`/`lstrip`/`rstrip`, нормализаторы кроме NFC/Replace/Sequence.
  Для перечисленных моделей ничего из этого не нужно.
